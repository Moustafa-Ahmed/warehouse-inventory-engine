01 · The invariant

The entire design protects one promise.

“

For every product and warehouse, committed stock can never exceed physical stock—and one business event can change inventory at most once.

01

Atomicity

All related writes commit together or none of them do.

02

Isolation

Competing writers cannot make decisions from the same stale balance.

03

Idempotency

Repeating the same intent returns the same outcome.

04

Traceability

Every transition leaves an immutable, inspectable record.

03 · Mental model

The database becomes the single-file doorway.

A

Request A enters

Inside a transaction, it locks the exact inventory row and reads the authoritative balance.

B

Request B waits

It cannot acquire a conflicting lock. It waits instead of making a stale decision.

C

B re-evaluates

After A commits, B receives the lock and sees the new balance—then safely fails or reserves.

What the lock does not mean

It is not a long-lived reservation and it should never cover an HTTP call. It exists only for the short database transaction that validates and changes state.

04 · Accounting

Track physical stock and commitment buckets.

available=on_hand−reserved + picked + packed
On hand10Physically inside this warehouse.
Reserved4Promised, but not yet picked.
Picked3Removed from its storage location.
Packed1Ready to leave the warehouse.

Available = 10 − (4 + 3 + 1) = 2. Shipped and delivered quantities belong to shipment/order history because they have left warehouse stock.

06 · Defense in depth

The application decides. The database refuses corruption.

inventory constraints
UNIQUE (product_id, warehouse_id)

CHECK (on_hand_qty >= 0)
CHECK (reserved_qty >= 0)
CHECK (picked_qty >= 0)
CHECK (packed_qty >= 0)

CHECK (
  reserved_qty + picked_qty + packed_qty
  <= on_hand_qty
)
  • Foreign keys prevent orphaned reservation and shipment records.
  • Unique operation keys turn duplicate commands into observable no-ops.
  • Indexes cover product/warehouse lookup, open reservations, pending shipments, and expiry scans.
  • Integer quantities avoid rounding ambiguity for countable stock.
Important MySQL check

Confirm the deployed MySQL version enforces CHECK constraints. Keep the application validation even when the database does.

07 · Happy path

One reservation. One short transaction.

01

Recognize the intent

Look up the idempotency key. If already completed, return the previously stored result.

02

Lock inventory deterministically

Sort every requested inventory ID, then select the rows with FOR UPDATE in that same order.

03

Recalculate availability

Use the locked values. Never trust a balance read before the transaction.

04

Change all related state

Create reservation rows, increment reserved quantities, and append movement and transition records.

05

Commit, then continue

Only after commit may notifications, jobs, or external work observe the new reservation.

08 · Laravel shape

Make the critical section obvious in code.

ReservationService.php — illustrative shapeLaravel 13
return DB::transaction(function () use ($command): Reservation {
    $existing = Reservation::where('idempotency_key', $command->key)->first();

    if ($existing) {
        return $existing; // same intent, same result
    }

    $inventory = Inventory::query()
        ->whereKey($command->inventoryId)
        ->lockForUpdate()
        ->firstOrFail();

    if ($inventory->availableQuantity() < $command->quantity) {
        throw new InsufficientStock($command->inventoryId);
    }

    $reservation = $this->createReservation($command);
    $this->increaseReservedBalance($inventory, $command->quantity);
    $this->recordMovement($reservation, $command);

    return $reservation;
}, attempts: 3); // bounded deadlock retry

For multi-line orders, fetch every inventory row in a stable order before validating any line. Do not lock one row, perform work, then discover another row later.

11 · Repeat safety

Retries are normal. Duplicate effects are not.

Operation requestEach mutating form or system caller supplies an idempotency key; a repeated reserve/release command returns its stored result.
DatabaseUNIQUE constraints are the final arbiter when two identical requests arrive simultaneously.
QueueShouldBeUnique reduces duplicate work, but the database guard still protects correctness.
Provider requestReuse one stable request key after timeouts so the carrier does not create a second shipment.
Provider webhook receiptPersist the raw callback under UNIQUE(provider, external_event_id) before applying its transition. On conflict, resume an identical unprocessed receipt and reject a mismatched raw body.
Key idea

Queue uniqueness is an efficiency feature. Domain-level database idempotency is the correctness guarantee.

12 · External boundary

Never hold a row lock while waiting on the internet.

01 · DB

Claim shipment

Short transaction changes pending → submitting and commits.

02 · HTTP

Call provider

Outside the transaction, with timeout and stable request key.

03 · DB

Record response

Lock shipment; store accepted, permanently failed, or unknown result.

04 · WEBHOOK

Store provider webhook receipt

Insert the raw callback into provider_webhook_receipts under UNIQUE(provider, external_event_id). On conflict, compare the immutable raw body: reload or claim an identical receipt, retry or enqueue it when processed_at is null, and reject a mismatched body without applying an effect.

05 · DB

Apply once

Lock affected rows, ship packed quantity, append movement, commit.

Dispatch follow-up jobs after commit. If delivery to the queue itself must be guaranteed, persist an outbox message in the same transaction and publish it asynchronously.

13 · Failure design

Every failure gets a deterministic answer.

Provider times outMark the outcome unknown; retry with the same provider key or reconcile.A timeout is not treated as a definite failure.

14 · Multiple locks

Deadlocks are managed by ordering + retry.

Warehouse transfer

Lock both source and destination inventory rows in ascending ID order. Transfer only available quantity—not reserved, picked, or packed stock.

Multi-line order

Resolve all inventory IDs first, sort them, lock them together, then validate the complete order before writing.

stable lock orderingdeadlock-aware
$inventoryIds = collect($lines)
    ->pluck('inventory_id')
    ->unique()
    ->sort()
    ->values();

$inventories = Inventory::query()
    ->whereKey($inventoryIds)
    ->orderBy('id')
    ->lockForUpdate()
    ->get();

// DB::transaction(..., attempts: 3)

Deadlocks are not data corruption. The database aborts one transaction safely; Laravel can retry the complete transaction a bounded number of times.

15 · Required simulation

Make the fake provider teach the architecture.

Immediate success

The provider accepts the stable request key and returns a provider shipment ID. The job records “accepted”; inventory is consumed only at the chosen business milestone.

  • Persist request and response.
  • Do not depend on in-memory job state.
  • Later duplicate success remains a no-op.
16 · Proof

Test the dangerous interleavings, not just interface responses.

Two database connections compete for one remaining unit; exactly one succeeds.
The same idempotency key is submitted twice; balances and movement count change once.
An exception after the reservation insert rolls back inventory, history, and reservation together.
A partial pick, pack, ship, and release preserves every quantity invariant.
A duplicate provider webhook produces one shipment transition and one inventory movement.
A timeout followed by success with the same provider key creates one external shipment.
A permanent failure never consumes on-hand inventory and leaves an auditable reason.
Transfers and multi-line orders lock rows in the same deterministic order.
Testing caveat

SQLite cannot prove MySQL row-locking behavior. Run the concurrency suite against the same database engine used in production.

17 · Judgment

Know what you bought—and what it costs.

Why it fits

  • Strong, understandable consistency.
  • Excellent fit for a single-primary MySQL deployment.
  • Natural Laravel transaction APIs.
  • Auditable without full event sourcing.
  • Feasible to finish and test in an interview task.

What to monitor

  • Lock wait duration and deadlock rate.
  • Transaction duration and hot SKUs.
  • Queue retry and provider timeout rates.
  • Unprocessed webhook/outbox records.
  • Movement-to-balance reconciliation drift.

If contention later becomes extreme, the next move is not automatically event sourcing. First measure hot keys, shorten transactions, partition work, or serialize commands per inventory key.

18 · Tell the story

Your two-minute design defense.

“I chose pessimistic row locking because inventory correctness is the dominant requirement. Each command is an idempotent, short transaction: it locks authoritative balances, validates the invariant, updates state, and appends history atomically.”

Then mention failure

Jobs and webhooks are at-least-once, so database idempotency makes reprocessing safe.

Then mention boundaries

External calls happen outside locks; post-commit work uses after-commit dispatch or an outbox.

Then mention trade-offs

We accept bounded lock contention and deadlock retries for a simpler consistency model.

19 · Keep this

The never-forget checklist.

  • Lock the row before checking availability.
  • Keep transactions short and free of network calls.
  • Lock multiple rows in deterministic order.
  • Retry deadlocks, not arbitrary business failures.
  • Make quantity conservation explicit.
  • Use database uniqueness for every operation key.
  • Treat queue uniqueness as an optimization.
  • Persist ProviderWebhookReceipt first, resume an identical unprocessed duplicate, and reject an identity/body mismatch.
  • Append movement and transition history atomically.
  • Test concurrency against MySQL.
